## 一、为什么这套回归可信：期望值不来自被测引擎

这是整套设计的核心。书里对每一卦印了**两组互相独立**的信息：

| | 内容 | 在本回归中的角色 |
|---|---|---|
| ① 卦画 | 六爻阴阳（`′`/`″`）、哪一爻「动」 | **引擎的输入** |
| ② 装卦 | 每爻六亲、纳甲地支、世应、变卦、六神、伏神 | **断言的期望** |

引擎的职责正是「由卦画推出装卦」。于是 ①→② 构成一次天然的 golden test：

```json
"head": "例：辰月戊申日占父近病，得乾为天变天小畜。",
"raw6": ["父母戌土′世              妻财卯木′", "…"],   // 书上的原文
"ben":  [{ "lq": "子孙", "zhi": "子", "yang": true, "moving": false, … }]  // 由原文解析
```

期望值 100% 由古籍印刷内容提供，**不存在「先跑引擎、再拿引擎输出当期望」的自证问题**
（本仓库历史上有过 `eq('甲日六神起', C.BEASTS ? '' : '', '')` 这类恒真空断言，故此处刻意规避）。

> 唯一的例外是「卦名 → 卦画」这一步：古籍把卦画以卦名文字印刷，解析时需要查一次
> `data.js` 的静态 `HEXNAMES` 字典。这属于**输入规范化**（命名约定），与被测的
> 「卦画 → 装卦」算法无关——字典错了会立刻在纳甲地支上暴露。

## 二、等价性论证：为什么不必把节气表前推到康熙年间

《增删卜易》卦例作于清康熙年间（约 1660–1690），早于本项目节气表下限 1900。
但**古籍卦例只记「月建 + 日辰干支」（如「辰月戊申日」），不记公历年份**——所以不需要知道年份。

`tests/guji/lib/ganzhi.mjs` 反过来做：在 1900–2100 内搜索一个「月支与日干支都与古籍相同」的
日期，用现代日期等价驱动引擎。这一步成立的前提是——**断卦规则链不依赖年柱与时柱**：

```
$ grep -nE "yearGZ|yearIdx|hourGZ|hourZhi|\.year|\.hour" public/core/analyze.js
（无匹配）
```

`analyze.js` 读取的 `pillars` 字段仅有：

- `monthZhi` —— 月令旺衰（`wangXiangXiuQiuSi`）、月破、相刑相害
- `dayZhi` —— 日辰生克、日冲（暗动/日破/冲散）、日合
- `dayGan` —— 六神起例（经 `beastStart`）
- `kong` / `kongStr` —— 旬空

全部只与「月支 + 日干支」有关。年柱、时柱不参与任何判定，故等价驱动不损失任何信息。

> 反过来这也说明：**若将来 `analyze.js` 引入了年柱或时柱依赖，本回归的等价性前提即被破坏**，
> 届时需改为按真实公历年份（并把节气表下限前推）驱动。

## 四、排盘对账断言了什么（《增删卜易》六行卦体）

每条卦例断言 **28 个字段**：

- 本卦 6 爻 × {纳甲地支、六亲、是否世、是否应}
- 变卦 6 爻 × {纳甲地支、六亲、是否世、是否应}（卦中有动爻时）

覆盖的算法：京房八宫卦序（世应定位）、八卦纳甲装配、六亲以本卦宫五行论、变卦六亲仍以本卦宫论。

> **诚实的边界**：断言数量虽大，但算法维度集中在「卦画 → 装卦」这一族。
> 月建/日辰本身不参与排盘（纳甲与日期无关），故排盘对账**不覆盖历法**——历法由
> `test-diff.mjs` 的三库差分（104,780 字段）负责，两者互补，不是重复。

## 五、表格式语料：六神与伏神对账（《卜筮正宗》）

《卜筮正宗》十八论等处的卦例是**表格**排版（占事/卦名/卦宫/空亡/缺爻/六兽/世应/卦/干支/六神/伏神…），
与《增删卜易》的六行卦体完全不同，故单设一支导入器 `tools/guji-import-bszz.mjs`。

### 5.1 这一支能对账什么、不能对账什么

表格**只印「日干 + 月建」，不印日支**，且相当一部分卦例（67/197）连日干也未印。因此：

| 字段 | 是否对账 | 理由 |
|---|---|---|
| 纳甲地支 | ✅ | 只取决于卦画 |
| 六亲 | ✅ | 只取决于卦画与卦宫 |
| **六神** | ✅（有日干时） | 只取决于**日干**（甲乙起青龙…壬癸起玄武），与日支无关 |
| **伏神** | ✅ | 只取决于卦画与卦宫（本宫首卦同位） |
| 世应 | ❌ | 该转换文本的世应列存在整体串行，不可信（此维度已由《增删卜易》覆盖） |
| 日冲/暗动/月破等 | ❌ | 缺日支，不在本语料射程 |

等价驱动用 `dateForDayGan()`：只要求「日干相符」，月支/日支取任意值即可——
因为上表所列的四个字段都与它们无关。这是 §二 等价性论证的一个更强的应用。

### 5.2 伏神的对账口径

伏神按**值**对账而非「位置」：**书上印出的伏神，必须能在引擎侧找到同值伏神**
（引擎的 `pan.lines[i].fu`）。不校验伏神挂在第几爻，原因是该转换文本的伏神列与
「伏」标记存在整行错位（如 `火山旅` 的「亥官」被渲染到二爻而行、`天火同人` 凭空多出
一份右栏的「巳官」）。值层面的对账仍能抓住真实错误——见下图自检。

引擎侧的伏神实现（`paipan.js`）：

```js
const pureZhiC = TRIG[benInfo.palace].najia[i];   // 本宫首卦同爻位
if (missing.indexOf(liuqin(palaceWx, ZHI_WX[zhiIdx])) >= 0) fu = { lq, zhi, … };
```

即「本宫首卦同爻位之干支，若其六亲在本卦中缺失，即为伏神」。这与《卜筮正宗》
同页的《飞伏定例》原文口径一致：

> 遁者退也．卦中缺妻财，子孙，**以干卦第二爻寅木伏于本卦第二爻午火之下**；午火是飞神，寅木是伏神…

### 5.3 六神

引擎侧：`BEASTS[(beastBase + i) % 6]`，`beastBase` 由日干定。书侧的期望值来自表格
「六兽」列，且同书《六兽歌》印有明文：

> 甲乙起青龙，丙丁起朱雀，戊日起勾陈，己日起腾蛇，庚辛起白虎，壬癸起玄武。
> （按六兽以起卦者为主，由初爻装至六爻）

130 条印有日干的卦例（780 项六神断言）中，引擎与书本一致率 98.5%；余下 12 项（2 条）
系该书**栏内自相矛盾**（六神起青龙而行内日干印作「庚」），已登记。

## 六、断语断言：用书里的话反查规则链

排盘对账只验证「装卦算得对不对」。断卦规则（暗动、日破、月破、旬空、冲散……）要靠
**书里明确写出的断语**做期望，人工核对后录入 `cases/zengshan-boyi.json`。

`expect` 支持五种形态：

| 形态 | 含义 |
|---|---|
| `{ "trend": "凶" }` | 整体旺衰粗判 |
| `{ "tag": "日冲", "rule": "日破" }` | 用神判定链中须出现该 `tag:rule`；只给 `tag` 则放宽到「出现该 tag 即可」 |
| `{ "atLine": 0, "monthGrade": "相" }` | 单爻视角：该爻在本月建下的旺相休囚死（`atLine` 0–5 = 初爻→上爻） |
| `{ "atLine": 1, "dayChong": "andong" }` | 单爻视角：日冲判定 kind（`andong` 暗动 / `ripo` 日破 / `chongsan` 冲散） |
| `{ "atLine": 5, "dongBian": "回生" }` | 单爻视角：动变判定 kind（`回生`/`回克`/`进神`/`退神`/`比和`/`化泄`/`化耗`） |

「单爻视角」的存在是必要的：用神只能选一个，而书里常点名**非用神**的爻
（如「戌日冲辰父而暗动」），此时需直接对那条爻断言。

### 驱动日期的三级弱化

古籍只记「月建 + 日干支」，不记公历年份，故用等价日期驱动。本轮为取材更边缘的卦例，
把等价驱动再向下弱化了两级：

| 级 | 字段 | 保证 | 可用于断言的字段 |
|---|---|---|---|
| 常规 | `monthZhi` + `dayGZ` | 月支、日干支均正确 | 全部 |
| 二级 | `dayGZOnly` | **仅日干支**正确（月建任意） | 只依赖日辰的项：日辰生克 / 日冲 / 日合 / 旬空 / 六神 / 伏神 |
| 三级 | `date` | 仅一个合法日期（用于原书未系月日者） | 只与卦画有关、与日月无关的项：纳甲地支 / 六亲 / 飞伏五行生克 |

⚠ 用二、三级驱动的用例，**不得**断言任何依赖月建的项（旺相休囚死、月破、月建生克、
真空之「休囚无扶」分支），其 `note` 均已注明。这类用例的价值在于：原文断语明载该判定，
而该判定在结构上确实与月建无关。

## 七、已登记分歧

**`zsby-0542`：辰月戊申日占父近病，「申日冲寅木而暗动」**

- 原文作「**暗动**」；
- 本实现按「旺相休囚死」口径判寅木在辰月为「**囚**」（木克土，克令者囚），故作「**日破**」。
- 同书〈增删黄金策千金赋〉又明言「**休囚为日破，不为暗动**」，与本实现一致——**同一部书内两处口径不一**。

处理：**保留实现口径，登记分歧，不改实现**。该用例仍参与断言（锁定现状），
若将来有人按野鹤此处口径改动实现，测试会变红，提醒同步更新本表。

**`zsby-3190`：子月癸酉日自占婚，「戌土虽值旬空，动不为空」**

- 原文作「**动不为空**」——野鹤〈旬空章第二十六〉明言「旺不为空，**动不为空**，
  有日建动爻生扶者不为空」，且此处是以**实占卦例**证成（「果于次日巳时允婚」）；
- 本实现判为「**真空**」：`ruleXunKong` 先算 `zhen = 月破 || (休囚 && 无日辰生扶)`，
  为真则**直接 return**，未给「动爻不空」留优先级。戌土在子月为「囚」、日辰酉金不生扶，
  故落进真空分支（`analyze` 的 `trend` 随之判「凶」，与原文「必允」相反）。

两类分歧的性质**不同**，不可混为一谈：

| 条 | 分歧性质 | 定性 |
|---|---|---|
| `zsby-0542` | 暗动/日破的**口径宽窄**（旺相休囚死的判定边界） | 野鹤同书两处口径自相矛盾，属流派选择 |
| `zsby-3190` | 判定链的**优先级**（动爻是否先于「休囚」判空） | **实现缺陷候选**——野鹤以实占证成「动不为空」，本实现却无条件先判真空 |

处理：同样**保留实现口径、登记分歧、不改实现**（本轮未获改引擎逻辑的授权）。
`expect` 写实测值 `真空`，把现状锁定；一旦有人修正该优先级，测试立刻转红。

> 后者正是 golden test 的直接产出：**用例先把缺陷暴露出来**，而不是等用户反馈。
> 本轮新增用例前，该缺陷在 12,044 项断言下完全不可见。

> 这正是古籍回归的价值：它把「实现口径 vs 原书口径」的差异变成可见的、可追踪的条目，
> 而不是藏在某个角落的隐式假设。

## 八、语料文本缺陷登记（known-text-issues.json）

第三方录入/转换的古籍文本存在排版缺陷（td 错位、串栏、讹字）。这些缺陷会让
**书上的期望值本身是错的**，从而误报为「引擎不符」。

处理方式**不是静默跳过**，而是逐条回溯到定本原文、判定归属、并把结论与原文证据
登记在 `known-text-issues.json`：

- 每条含 `id`（语料条目）、`greps`（涉及的断言字段）、`verdict`、`reason`（附原文证据）；
- `run.mjs` 把登记条数**单独列出**（「※ 登记文本缺陷 N 处」），不与「通过」混同；
- 若某条的定性有误（其实是引擎错），改动引擎后该条**不会**变绿——需要人工复核，
  这正是希望的效果。

当前登记 **31 处**，全部经回溯原文确认，例如：

| 例 | 现象 | 定性 |
|---|---|---|
| `bszz-02651-L` 水风井 | 该栏六爻六亲全部按**兑宫**（金）论，而水风井在京房八宫属**震宫** | 卦宫列误标 |
| `bszz-02872-R` 水山蹇二爻 | 丙午应作**官鬼**，本栏印「妻财」，同栏其余五爻皆合兑宫 | 讹字（并连锁推出错误的伏神「巳官鬼」） |
| `bszz-03434-R` 六神 | 六神自初爻起青龙（＝甲乙日），同行日干列却印「庚」 | 栏内自相矛盾 |
| `bszz-00782-R` 火山旅三爻伏神 | 应为「亥**官**鬼」，印作「亥父」 | 讹字（同页《飞伏定例》未以亥为父母） |

> 结论：**12069 项断言全部通过；31 处差异逐条回溯定本原文后，均定性为第三方转换文本缺陷，引擎侧零分歧。**
> （另有 2 处**口径分歧**登记于 §七，性质不同——其中 1 处为实现缺陷候选。）

## 九、怎么新增一例

### A. 六行卦体（《增删卜易》式）→ 进排盘对账

1. **确认原文有完整装卦**。书里若只写「得某卦」而无六行装卦，无法对账。
2. 跑 `npm run gen:guji`（会自动重下原文并重新解析）。
3. 在语料里按行号定位：

   ```bash
   node -e "const c=require('./tests/guji/corpus/zengshan-boyi.json');
   console.log(c.cases.filter(x=>x.line>1500&&x.line<1520).map(x=>x.line+' '+x.head).join('\n'))"
   ```

### B. 表格（《卜筮正宗》式）→ 进六神/伏神对账

1. 跑 `npm run gen:guji:bszz`；
2. 按 `line` 定位：`node -e "…corpus/bushi-zhengzong.json…"`；
3. 若该表存在转换缺陷，在 `known-text-issues.json` 里补一条（**必须写清原文证据**）。

### C. 断语断言 → 进规则层

写进 `cases/zengshan-boyi.json`：

```json
{
  "id": "zsby-XXXX-<要点>",
  "title": "丑月壬子日占讼（一句话概括）",
  "chapter": "增删黄金策千金赋章第三十四",
  "bookLine": 1508,
  "quote": "原文断语逐字摘录（断言必须能回溯到这句话）",
  "note": "为何这样断言；若与原文有出入，写明判断依据",
  "monthZhi": "丑",
  "dayGZ": "壬子",
  "toss": [1, 0, 1, 1, 0, 1],
  "target": "shi",
  "expect": [{ "tag": "日冲", "rule": "日破" }, { "trend": "凶" }]
}
```

驱动日期三选一（见 §六「驱动日期的三级弱化」）：

| 写法 | 用于 | 不得断言 |
|---|---|---|
| `"monthZhi": "丑", "dayGZ": "壬子"` | 原书记全了月建与日辰（常规） | — |
| `"dayGZOnly": "丙申"` | 原书只记日辰（如「旧存占验丙申日占文书」） | 一切依赖月建的项 |
| `"date": "2000-01-01T12:00:00"` | 原书未系月日（宫首卦理论示例） | 一切依赖日月者 |

`knownDivergence: true`：原文口径与本实现不同时使用（见 §七），`expect` 写**实测值**并把现状锁住。

`toss` 自下而上，取值 `1` 少阳 / `0` 少阴 / `9` 老阳动 / `6` 老阴动。
语料里的 `ben` 字段可直接换算：`yang && moving → 9`，`yang → 1`，`moving → 6`，否则 `0`。
**优先从语料取 `toss`，不要手抄**——语料的装卦已由排盘对账验证过。

最后跑 `npm run test:guji`、`npm run test:guji:self` 与 `npm run guji:coverage`。

**铁律：`expect` 必须能回溯到 `quote`。** 不要先看引擎输出、再把输出抄成期望——那是自证，不是回归。
（唯一例外是「已登记分歧」用例：那里是**明知引擎与原文不同**而故意锁住现状，`note` 必须写明。）

## 十、变异自检：证明"全绿"不是空转

`selftest.mjs` 向期望值逐类注入已知错误，验证每一类都能被捕获：

```
排盘层      11 类（本卦地支/六亲/世/应、变卦地支/六亲/世/应、静爻位、卦画、日辰非法）
断语层      12 类（trend、tag:rule、atLine、月建、日辰、卦画致伏神消失、日干支致日冲飞神消失、
                   target 致持世不成立、期望 rule 置换〔化进神→化退神〕、日辰生扶→克伤、
                   月建致临月建不成立、真空↔动不为空〔锁定已登记分歧〕）
表格式层     7 类（六神单爻 / 六神整体错位 / 装卦地支 / 装卦六亲 / 伏神值 / 伏神六亲 / 卦画）
合计 30 / 30 捕获
```

它同时抓出过几个**真实的设计边界**，都记在此处备查：

- 「篡改月建不影响排盘对账」——因为纳甲装卦只取决于卦画，与日期无关（见 §四的边界说明），
  故该类变异对排盘层无效，只对断语层有效。
- 变异必须选「语义上真的不同」的值。丑月→未月对午火等价（同为土，皆「休」），改了也不会变红；
  换成子月（水克火，转「死」）才构成有效变异。
- 「六神整体错位一位」这个变异项直接模拟了「日干取错」，是 §5.3 中那 2 条矛盾卦例的
  同型错误——自检能捕获它，说明该维度确实在对账，而非摆设。
- 断语层第 12 类变异是**分歧的回程校验**：把 `zsby-3190` 的期望由实测值 `真空` 改回
  原文口径 `动不为空`，测试立即转红。这证明 §七 登记的分歧不是文字备忘，而是被测住的。
