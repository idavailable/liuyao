### 5. 首轮不缓存的代价 —— 已量化，可以保持

> **晚：** 「63–98 秒」那个数字是 deepseek 的。实测 gemini 首轮真生成
> 8–20 秒（3.6）/ 12–19 秒（3.8），deepseek 37–55 秒。skipCache 的代价主要落在
> deepseek 上，gemini 侧完全可接受，**不必为缓存策略回退**。

为了不让残篇被缓存固化，首轮断卦不再命中缓存。代价：同一盘重复断卦从
**秒回**变成 **63–98 秒**。

可选方案（都没做）：命中缓存时先做完整性校验、坏了就跳过缓存重取。
但这要改缓存策略，建议**先看人工测试里「慢」到什么程度**再决定。

`yingqiWindow(pan, analysis)` 天生不知道用户在问什么，只会把「出空／冲空／值日／
出月／逢冲」换算成第几日。本轮只给「占天时 + 题面确定某日」开了一个口子
（第三参 `opts.fixedDay`），跨月事项的「窗口是日级、应期是月级」仍靠前提块文字
约束（`effRank >= 4` 时写「与【应期窗口】的关系」一段）。

彻底做法是把 span 整个传进窗口层做同域裁剪——但那会改动所有盘的窗口取值，
需要先攒对撞样本（同盘两问、只差时间跨度的对照），否则等于用规则改写引擎输出。

### 5. `DEEPSEEK_PREFIX=first` 暂不设为默认（2026-11-12）

first = 首次请求就带正文前缀，**等于关掉思考**（实测 reasoning_tokens 0 vs 254），
同一盘面 3 次：9.3/9.5/10.3 秒、951–1191 字，比普通 lean 模式（27–75 秒）快 3–7 倍。

暂不设默认，原因是**结构化五行会漏**：三篇里有三篇缺「前提完整性」行（无思考时它把
结尾五行压成四行），而前端 `parseConclusion` 靠那行显示前提状态。第 4 次（补前缀帧后）
没漏，说明是概率性的、不是必现。

**要不要转正，取决于一件事**：在 lean 提示词里把「结尾五行缺一即不合格」写成不可省的
硬约束后，first 是否还能稳定五行齐全。若可以，延迟能从 27–75 秒降到 10–15 秒，
且完全不烧推理 token。样本门槛：10 次里 ≥9 次五行齐全。

另：first 只在 `api.deepseek.com` 域名下放开（代码已加门槛）。自定义中转只代理 `/v1`，
`/beta` 是 404，而 first 模式本身不重发，首次即死——这类部署必须留在 retry 档。

**#6 的边界（改的时候最容易过头的地方）**：只补「已命中两支（动/变/日月）+ 第三支在卦中安静」。
若放宽成「静爻全进候选池」，随机盘会新增 339 个局次（400 盘样本），噪音压过信号——
静爻终究不能引动，只能补位，不能起局。


**已修但容易误记的两条**（免得下轮返工）：

- 火在亥月，四时旺衰为「死」、长生十二宫为「绝」，**两者都对**，模型说「临死地」不算错；
  引擎同一份输出里「（死）」与「绝地」并存是两套体系，不是自相矛盾。
- 「合而变冲」是**引擎文案**的锅（`ruleGuaXing` 对非六合卦也套用〈六合章〉措辞），
  模型只是照抄；已在源头改为「动而变冲」并加断言，不要再当模型幻觉处理。

**已排除的伪缺口**：`11月内` / `甲子日` 在兜底刻度下不再报错，属
2026-11-12「假设不能当证据」的有意变更，不是漏判；`出分当日` / `11月下旬出分时`
走流程节点判定，本就放行。
