## 一、规则库是什么

断语规则库指 `public/core/analyze.js`（断卦符号层）：它接收排盘结果，按**规则判定链**
输出结构化断语，每条断语是一个对象 `{ tag, rule, text, basis }`——`basis` 是典据字段，
注明该判定依据的原书与条文（README「技术要点·断卦符号化」）。同时输出：

- `trend`：吉 / 凶 / 平 / 待审 四值粗判，由**规则汇聚表**求得，**不由任何算术分值决定**
  （M3 验收标准：源码中禁止出现 `score` 字样；见 README「验收标准 M3」）；
- `yingqiClues` / `yingqiLayers`：应期**线索**（扁平线索 + 主/辅/险三层归档），
  只出线索不下应期结论（README「技术要点·排盘引擎」「上层契约层·应期三层」）；
- `yingqi-window`（应期域层）：把线索换算为「区间＋置信度＋依据＋下调原因」，
  其中置信度是**盘面要素的自洽度**，不是命中概率；真空、真月破、取不到用神三态一律
  `blocked` 拒答（docs/optimization-2026-10-24.md §二.2）。

判定口径一句话：**京房纳甲体系，专凭五行生克，不用神煞**（`public/core/analyze.js` 文件头声明）。

引擎之上有四个不参与排盘的上层契约模块（敏感问题分流、领域方法注入、断语事实审计、
推理一致性审查），属产品行为而非断语规则本体，本文不展开，见 README「上层契约层（M15）」。

## 三、各类别依据的古籍与门派

### 3.1 语料书目

两书皆为公有领域传世定本，文本取自
[daizhige-org/daizhigev20](https://github.com/daizhige-org/daizhigev20)
（来源：tests/guji/README.md §书目表；条数为 `npm run test:guji` 实跑输出）：

| 书目 | 版本 | 语料条数 | 对账维度 |
|---|---|---|---|
| 《增删卜易》 | 清·野鹤老人传，李文辉增删，康熙三十年刊本（六行卦体排版） | 207 条排盘对账＋65 条断语用例 | 纳甲地支 / 六亲 / 世应 / 变卦 / 断语规则链 |
| 《卜筮正宗》 | 清·王洪绪（表格排版） | 197 条装卦对账＋3 条断语用例 | 纳甲地支 / 六亲 / **六神** / **伏神** |

排盘对账的断言构成（来源：tests/guji/lib/check.mjs）：《增删卜易》每条断言本卦 6 爻 ×
{纳甲地支、六亲、是否世、是否应}，卦中有动爻时再断言变卦同构字段；《卜筮正宗》表格
断言纳甲地支与六亲（仅印日干的卦例加断六神，伏神按**值**对账）。全部语料合计断言
**12144 项**，实跑通过 12144、失败 0（`npm run test:guji` 输出，2026-10-24）。

六神一项：197 条表格卦例中 67 条未印日干（六神项略，run.mjs 实跑输出），印有日干的
130 条共 780 项六神断言，引擎与书本一致率 98.5%，余下 12 项（2 条卦例）系该书
**栏内自相矛盾**（六神起青龙而行内日干印作「庚」），已登记为文本缺陷
（tests/guji/README.md §5.3；对应登记条目见 tests/guji/known-text-issues.json）。

### 3.2 门派口径（显式登记的取法）

以下口径是**流派选择**，本仓均显式声明而非默认混合（来源见各条）：

1. **体系**：京房纳甲（八宫卦序变爻法、纳甲装配、六亲以本卦宫五行论）——两书同源，
   装卦维度由 404 条语料对账背书（tests/guji/README.md §四）。
2. **断法范围**：专凭五行生克，**不用神煞**（天德、天厨、三合神煞等一律不做）——
   `public/core/analyze.js` 文件头；未吸收理由见 README「上层契约层·吸收取舍」。
3. **夜子时两流派显式开关**：`LY.nightZiMode` 默认 `'day'`（夜子时正法：日柱归当日、
   时干按次日日干五鼠遁），可切 `'next'`（换日说：整体归次日）；两派分别与
   najia/lunar-javascript、iching-shifa 对齐（README「技术要点」）。
4. **占时口径固定北京时（UTC+8）**：节气表与现场取时同源，不读本机时区（README「技术要点」）。
5. **取用神次序**：伏神多现时按「临世应者 → 月令旺相者 → 在前之爻」古法次序
   （`public/core/analyze.js` pickYongshen 注释）。
6. **五行关系五值完备**：比和 / 得生 / 受克 / 泄 / 耗，规则禁止 `else` 兜底猜关系
   （`public/core/analyze.js` relation5 注释；README「功能」附历史 bug 记录）。
7. **真空以「安静」为前提，动爻永不真空**：此口径由古籍用例反向修正引擎后定案
   （§四「已修正项」；tests/guji/README.md §七）。
8. **trend 非评分**：吉凶由规则汇聚表驱动；卦型/生旺墓绝/三神等末三族只陈述不入 trend，
   理由是「吉凶随占类翻转或与既有维度重叠」（README「验收标准 M16 断卦三族」）。

未定案的流派参数：**取用神之争**（如「舍其休囚而用旺衰、舍其月破而用不破」类取舍）
目前**无显式参数**，是已登记的未做项（docs/optimization-2026-10-24.md §一「六·方法 2
两派并置」行、§四）。改此类口径须先给每派各写一套 golden 期望并经 tests/guji 背书，
否则失去「同盘同解」这条可验证承诺（docs/optimization-2026-10-24.md §四）。

## 四、口径分歧如何标注

### 4.1 标注机制

tests/guji 把「实现口径 vs 原书口径」的差异分成三类处理（tests/guji/README.md §七）：

| 类别 | 判定 | 处理 |
|---|---|---|
| **文本缺陷** | 差异源于第三方录入/转换的排版缺陷（td 错位、串栏、讹字） | 逐条回溯定本原文定性，登记于 `tests/guji/known-text-issues.json`（当前 12 条登记条目；实跑按字段计 31 处排除项，`npm run test:guji` 输出「※登记文本缺陷 31 处」），不做静默跳过 |
| **口径分歧** | 原书口径 ≠ 实现口径，且属**原书自相矛盾**（同一部书内两处口径不一）的流派选择 | **保留实现口径、登记分歧、锁定现状**：用例标 `knownDivergence: true` 并写实测期望，仍参与断言——将来有人改口径，测试转红，提醒同步更新分歧表 |
| **缺陷（已修正）** | 原书有明文依据、实现确实错了 | 回溯原文取证后**改实现** |

## 五、已知局限

1. **覆盖率 82.1% 的含义**：分子只统计「被断语用例断言到的 rule」，未覆盖的 14 条
   （§2.2）逐条有「不该建」的原文依据；为凑数硬造用例会把引擎口径固化成「标准答案」。
   正确的提升路径是先回头修引擎标签体系（如把「泄气于月/克月建」合并回原书「休囚」
   一档），而不是编用例（tests/guji/README.md §八「结论」）。
2. **断语用例里有一部分是「定义型」**：游魂/归魂/仇神/烈火煎金/论生不论墓/论生不论绝/
   化长生/化旺在两书里**没有任何实占卦例显式提及**，用例取章中点名卦或构造卦画＋假定
   月日，期望仍取自书中规则原文而非引擎输出（tests/guji/README.md §六「M16 三族」）。
3. **语料侧局限**：《卜筮正宗》表格转换文本的世应列整体串行（不对账该维度，由
   《增删卜易》语料覆盖）、变卦列已提取但未纳入断言；排盘对账不覆盖历法——历法由

   区间与置信度，真空/真月破/取不到用神三态一律拒答，不用「近期会有变化」兜底

   同一判定链）与**有据可查**（每条断语带典据），不是预测效力。产品内已有的命中率

## 七、引用边界

本仓对断语规则库的定位受四条硬边界约束（README「M16·边界（诚实声明）」；
docs/optimization-2026-10-24.md §一「七·四件不做」行）。引用本页时请注意：

1. **不宣称预测效力**：规则库保证的是确定性（同盘同解）与可溯源（逐条典据），
   不保证也不暗示「断得准」。任何引用不得把 12144 项断言、82.1% 覆盖率、98.5%
   一致率等数字表述为「准确率」——它们是**对账一致性与覆盖广度**的度量。
2. **不做单点打分**：规则库无评分制（M3 起源码禁绝 `score`），吉凶只有
   吉/凶/平/待审四值粗判，由规则汇聚而非加权求和得出。引用时不得为其构造分数。
3. **不做医疗、法律、财务等专业决策的替代**：敏感问题确定性分流三档
   （block / advisory / pass），确诊类医疗等五类问题不进入断卦（README「验收标准 M15」）。
4. **无付费化解**：不存在任何「化解」「改运」类服务与引导。

本文描述的规则库只是「把古籍明文规则做成可单测的确定性判定链」这一工程事实的说明；
它在传统断卦体系内部的完整性、以及该体系与现实的对应关系，均不在本页可断言的范围内。
